# BITFSAE GitHub 工作流

## 目标

让 BITFSAE 的改动可审查、可追溯，不夹带凭据或生成产物，同时尊重各仓库现有规则和维护者的选择。

## 团队约束

- 基于最新 main 建立特性分支。不要直接向 main 推送，也不要改写已发布历史。
- 遵循仓库现有的分支和提交约定；没有约定时使用清晰前缀（如 feat/、fix/、docs/）和简洁的 type(scope): subject 信息。
- 组织内协作使用分支和 Pull Request，项目明确采用 Fork 工作流时除外。
- 仓库有 PR 模板时使用模板。说明改了什么、为什么、如何验证及仍有哪些未验证；不得声称未测试的结果已通过。
- 向相关负责人请求审查，处理修改意见，批准后再合并。
- 改动影响对外消费的 CAN 或遥测定义时，先更新并审查 BITFSAE/vehicle-interfaces，再适配消费项目。内部重构、合规恢复修复和项目专属配置不需要这样做。
- 绝不提交凭据、密钥或生成产物。遵循仓库 .gitignore，不要强制添加被忽略文件。
- 仓库专属指令和既有约定优先。

## 检查

- 确认基线是最新 main，且工作在特性分支上。
- 确认改动是否影响对外消费的 CAN 或遥测定义。
- 确认差异中没有凭据、生成产物、被忽略文件或无关编辑。
- 确认验证证据与真实执行内容一致。
- 确认审查人是相关负责人，且合并方式符合该仓库的选择。

约束缺失或无法核实时，不得声称符合规范，应报告具体缺口和所需动作。
