# 写作风格

适用于文档、代码注释、更新记录和报告。BITFSAE 文档使用中文编写，下文用词示例均为中文。

## 目录

1. 语气
2. 避免的用词
3. 正面表述与否定句
4. 平实用语
5. 顺序与结构
6. 完整性
7. 修订自查

## 1. 语气

动手前先按文档用途和读者确定语气：

| 文档用途 | 常见文档 | 语气要求 |
| --- | --- | --- |
| 仓库规范与契约 | `README.md`、接口文档、配置表、`CHANGELOG.md`、代码注释 | 最克制、精确：只写是什么、做什么、在什么条件下 |
| 设计计算与审车材料 | ESF/SES 计算书、载流或强度校核、审车答辩材料 | 客观严密：写清边界条件，把结论和安全裕度摆在最前 |
| 内部学习、积累与评审 | 技术笔记、原理梳理、方案对比、问题复盘、排错与交接 | 平实好读：分清主次与因果，允许用直观对比、量级反证和明确工程判断 |

- 章节较长或有多个部分时，先概括再展开；标题和首句直接体现状态或结论。
- 读者需要据此决策，或避免改坏设计时，写明动因和收益。
- 不写口号、说教、填充和重复。

## 2. 避免的用词

- 商业化、互联网用词：赋能、打造、一站式、极致、无缝、强大、丝滑、闭环、抓手等。改写成具体功能。
- 夸张、情绪化、攻击性用词和空洞自评，如“设计优秀”“非常稳定”“致命”“硬伤”“站不住脚”。改写成实测数值、成立条件，或紧跟定量依据的工程判断（如“明显错误”“相互抵消”“可以忽略”）。
- 绝对化词汇：最、完全、绝对、100%、一定、永远、彻底。改写成实际范围、条件或数量。已定义的量、参数名（如“最大充电电流”“100% 占空比”）以及带明确量化边界的判断（如“占比 1.4%，可以忽略”）照常使用。

## 3. 正面表述与否定句

- 规则和结论正着说：先写“是什么、用来干什么”，再给判断规则。
- 完成条件用可观测信号表达，如“以保存等待位清零为准”“看 X 字段”。
- “不是……而是……”少用，否定句尽量少。简短、一眼能懂的否定句照常使用。
- 澄清只加在读者可能真实误解的位置，并给出原因或机制。没有原因的否定句（如“不代表 X”“不能只看 X”）删掉。
- 写如何处理时，同时写明原因。

示例：

- 改前：「保存是否完成，不是看命令应答，而是看保存等待位。」
- 改后：「以保存等待位清零为准。命令应答只表示命令已收到，此时数据可能仍在写入。」

## 4. 平实用语

- 标题直接说明本节内容。
- 用常用词和短句。抽象词如门控、语义、消费、落盘、原子、临界区，改写成具体动作，如“写入 Flash”“读取”。
- 协议或标准要求使用某个名称时，首次出现处用直白语言解释。
- 说明错误或矛盾时，直接摆出反常的量级或物理后果（如“对应宽度需 223 mm，不符合箱体尺寸”），少用绕弯子的书面长定语。

## 5. 顺序与结构

- 文档按“职责 → 已实现流程 → 接口/协议 → 异常 → 调试验证”的顺序组织。
- 已实现行为与后续工作分开。标定、联调、待确认参数和已知不足放在文档末尾或附录。
- 少见故障的处理放在主要流程之后，写清触发条件、动作、原因和不受影响的流程。
- 同一结论只完整说明一次，其他位置简短引用。

## 6. 完整性

目标是读者只看文档就能理解全部实现。正确和完整优先于简短。精简文字时，保留理解代码、接口、参数、动作条件、处理顺序、各项设置的原因和验证方法所需的信息。

## 7. 修订自查

逐条以“读者能否一眼看懂”为准判断，不机械执行。

- 规则正着说是否更清楚？
- 每个完成条件是否给出可观测信号？
- 有没有无原因的否定句？
- 同一结论是否多次完整说明？
- 有没有商业化用词、自评式论断，或非定义量的绝对化词汇？
- 语气是否符合文档用途，核心结论、问题轻重和因果关系能否第一遍扫读就抓住，没有因过度温和而变含糊？
- 是否缺少理解实现所需的信息？
