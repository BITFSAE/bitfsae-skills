1. 文档归属

5. 外部接口文档

## 1. 文档归属

每条详细事实只有唯一主所有者。从 README 概括并链接，不在多处维护独立副本。

| 信息 | 首选所有者 |
| --- | --- |
| 项目目的、快速上手、文档索引 | README.md |
| AI 编辑约束 | AGENTS.md、CLAUDE.md |
| 已发布变更与待办 | CHANGELOG.md |
| 公开协议或 API | 独立接口文档与模式 |
| 常改值 | 配置文档和命名代码定义 |
| 模块状态、算法、故障行为 | 模块文档 |
| 引脚、网络、电气假设 | 硬件文档与设计文件 |
| 构建、烧录、测试、调试 | 构建/开发文档 |

## 2. README

为决定项目是什么、从哪里开始的新队员编写。适用时按以下顺序：

1. 一段话说明目的和范围；
2. 文档索引；
3. 主要能力与排除项；
4. 简洁的硬件/运行时概览；
5. 带链接的公开接口摘要；
6. 源码树或主要模块；
7. 最短的已验证构建路径；
8. 安全或运行警告。

底层寄存器值、完整协议布局、长算法和详尽排障放在专门文档中。

## 3. AI 指令文件

用祈使规则说明 AI 应如何编辑和验证仓库，只包含稳定指令：

- 生成文件编辑限制；
- 新逻辑应放的位置；
- 第三方代码策略；
- 必须执行的构建/测试命令；
- 文档同步规则；
- 注释语言和清晰度要求；
- 仓库专属安全约束。

不写项目概览、易变硬件值、CAN 报文表、文件清单，或其他文档拥有的事实。AGENTS.md 与 CLAUDE.md 同时存在时保持一致。除非用户明确移除，BITFSAE 的 AGENTS.md 必须保留 DO NOT send optional commentary。

## 4. 更新记录与待办

使用易读的倒序 CHANGELOG.md：

- 未发布：尚未发布的工作；
- 未发布/待办：具体且仍需完成的工作；
- 带日期章节：已完成的交互行为、接口、构建变更、修复和迁移说明。

记录结果和兼容影响，而不是每次提交。不得声称未测试的特性已完成。仅当 todo.md 只是重复变更记录时才删除；若包含不属于发布历史的排期或归属信息则保留。

## 5. 外部接口文档

作为生产者和消费者之间的契约编写。紧凑概览 → 精确表格 → 错误行为 → 已验证示例。把解释与原始布局分开。

每个字段包含：名称、偏移、宽度、类型、字节序、比例、偏移、单位、范围、无效值和含义。说明时序、复位、重试、顺序、持久化与版本兼容。示例使用项目实际使用的实现语言。

DBC、OpenAPI、JSON Schema、Protobuf、公开头文件等机器可读定义应与正文保持同步。注意记录需要上游核实的临时名称。

## 6. 配置文档

以安全修改为目标。使用表格：

- 配置项和当前值；
- 代码符号或生成器位置；
- 单位和合法范围；
- 影响的行为或硬件；
- 必须同步更新的文档、测试、标定或消费者。

区分生成的外设配置、编译期策略默认值、运行时命令、持久化设置、标定值与密钥。说明重启/复位行为。不暴露真实凭据或私钥。

## 7. 模块与设计文档

模块有状态机、控制策略、并发、标定、安全回退、不直观算法或多个外部交互时创建。

建议结构：

1. 职责与边界；
2. 输入、输出和依赖；
3. 状态或处理顺序；
4. 时序与并发；
5. 配置；
6. 故障与回退行为；
7. 公开函数或集成点；
8. 验证与测试用例。

只有图表比简短列表更能解释关系或状态变化时才使用。不要复述每个函数体。

## 8. 硬件与构建文档

硬件文档：把逻辑功能映射到引脚、网络、外设、电平、极性、上拉、隔离、传感器地址和标定假设。区分原理图事实、软件预期与未验证板级行为。

构建文档：前置条件、精确支持的命令、输出路径、烧录/调试入口、生成器工作流与再生成检查。优先使用维护中的构建系统。只有已验证且有用时才保留备用构建路径。

## 9. 写作与维护规则

- 结构与用途匹配：README 导航，接口文档精确，配置文档面向任务，模块文档解释行为，更新记录概括变更。
- 先给结果或行为。缩写先定义一次。单位写在数值旁。
- 精确字段映射和配置优先用表格；原因和交互用正文。
- 从当前状态文档移除过期历史，保留在更新记录或版本控制中。
- 避免夸张声明、通用说教、重复警告，以及无助于队友操作或修改项目的文本。
- 每次相关代码变更时，在同一工作项中更新对应的所有者文档。
