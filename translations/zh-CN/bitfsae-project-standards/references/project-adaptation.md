# 项目适配

## 目录

1. 选择项目画像
2. 最小文档集
3. 不削弱标准地适配
4. 处理不确定性与遗留项目

## 1. 选择项目画像

根据维护者必须操作的对象和消费者依赖什么分类：

- 嵌入式固件或硬件控制器；
- 可复用库或驱动；
- 命令行或工程工具；
- 服务、桌面、Web 或移动应用；
- 数据处理、模型或分析项目；
- 实验或短期原型；
- 包含上述多种内容的 monorepo。

只使用相关标准。没有 CAN 的工具不需要 CAN 文档；公开库仍需要精确 API 契约和变更历史。

## 2. 最小文档集

### 嵌入式固件

- README.md
- 团队工具使用时才需要的 AGENTS.md 和 CLAUDE.md
- CHANGELOG.md
- 构建/烧录文档
- 硬件映射文档
- 有外部接口时提供接口文档及 DBC/模式
- 通用配置文档
- 控制、状态、安全或标定逻辑的聚焦模块文档

### 可复用库或驱动

- 带支持环境和最小示例的 README
- 公开 API 与错误/所有权/生命周期契约
- 适用时提供配置或移植指南
- 更新记录与兼容说明
- 测试或示例消费者

### CLI、应用或服务

- 带目的、安装、运行和测试路径的 README
- CLI/API/文件格式契约
- 配置和环境变量参考
- 非显而易见边界才需要的架构/模块文档
- 适用时提供更新记录、迁移说明和部署/运维指南

### 原型

文档保持精简但真实：目的、如何复现、输入/输出、已知限制与后续决策。不要制造没有项目特定信息的生产级文档。

### Monorepo

使用根目录 README 和共享规则进行导航与通用工作流。可独立构建或部署的组件应有自己的 README、接口/配置文档和更新记录归属。避免在每个子项目重复根策略。

## 3. 不削弱标准地适配

已有清晰布局时允许项目专属文件名与结构。评估文档功能而不是机械执行名称，工具必需文件（如 AGENTS.md）除外。

按风险、公开面、生命周期、团队规模和变化频率调整粒度。安全固件需要精确故障行为；一次性转换器可能只需要精确 CLI 和文件格式描述。

团队已有明确术语时保留。定义专业术语，但不要用含糊通用词替代有效领域语言。

## 4. 处理不确定性与遗留项目

- 删除看似过时的细节前查看历史，它们可能记录兼容性或硬件约束。
- 区分当前行为、历史行为和计划变更。
- 代码与文档冲突时，先测试或追踪实现再一起重写。
- 标记未核实的电气事实、上游字段映射、标定和部署假设。
- 全量重写会产生不可审查的变更时，逐步改进遗留文档。
- 工作区不干净时保留用户改动和无关工作。
- 只有未决选择会实质改变行为、兼容、安全或文档归属时才请求方向。
